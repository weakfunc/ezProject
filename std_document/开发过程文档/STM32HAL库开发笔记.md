## USART

### USART是什么

STM32F103C8T6上有三个串口：**USART1、USART2、USART3**。USART既支持同步也支持异步模式，实际开发中99%的场景都用异步模式，也就是平时说的"串口通信"。核心思想是两个设备之间用两根线（TX和RX）交叉连接，发送端按约定好的速率逐bit发出数据，接收端按同样的速率逐bit采样恢复数据，双方不需要共享时钟线，靠**波特率一致**来保持同步。

硬件连接最基本只需要三根线：TX → 对方RX，RX → 对方TX，GND ↔ GND（共地必须连）。注意TX和RX是**交叉**的，不是同名相连。F103各串口的默认引脚如下，引脚可通过AFIO重映射到其他位置：

| 串口   | TX引脚 | RX引脚 | 挂载总线 | 最高时钟 |
| ------ | ------ | ------ | -------- | -------- |
| USART1 | PA9    | PA10   | APB2     | 72MHz    |
| USART2 | PA2    | PA3    | APB1     | 36MHz    |
| USART3 | PB10   | PB11   | APB1     | 36MHz    |

USART1挂在APB2上，能达到的最高波特率比另外两个更高。除了最常用的异步模式外，USART还支持**同步模式**（额外输出CK时钟线，极少使用）、**单线半双工模式**（只用TX一根线，软件切换收发方向）和**LIN模式**（汽车电子低速总线协议）。另外还有两个可选的**硬件流控引脚**RTS和CTS，接收缓冲区快满时硬件自动通知对方暂停发送防止溢出，大多数简单通信不用流控。

### 数据帧与波特率

串口发送一个字节时，线路上的波形是：空闲状态高电平，先发1bit低电平的**起始位**，接着**8bit数据**（低位先发），最后1bit高电平的**停止位**。中间可插入一个可选的**校验位**（奇偶校验，大多数场景不启用）。最常见的配置是 **8N1**：8个数据位、无校验、1个停止位。

```
空闲(高)  ──┐   ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌───── 空闲(高)
           │   │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │
           └───┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘
           起始位  D0  D1  D2  D3  D4  D5  D6  D7  停止位
```

**波特率**是每秒传输的bit数，双方必须设成一样的值，常用的有9600、115200、460800等。以115200为例：每个字节实际占10bit（1起始+8数据+1停止），10 ÷ 115200 ≈ 86.8μs传一个字节，每秒最多约11520字节。波特率由BRR寄存器配置，CubeMX自动计算，但**实际波特率和目标值之间会有误差**，来源是时钟分频不能整除，误差在2%以内通信没问题，超过3%可能出错。HSE（外部晶振）比HSI（内部RC振荡器）精度高得多，要求可靠通信时建议用外部晶振。

### 接收方式

**轮询接收**调用 `HAL_UART_Receive(&huart1, buf, 10, 1000)` 阻塞等待收满指定字节或超时，期间CPU被完全占住，只适合最简单的调试。**中断接收**调用 `HAL_UART_Receive_IT` 后立即返回，每收到1字节触发 `HAL_UART_RxCpltCallback` 回调，在回调里处理数据并重新挂起接收。注意HAL的中断接收是一次性的，回调里如果忘了重新调用 `HAL_UART_Receive_IT`，串口就不再接收了。**DMA接收**让DMA硬件自动搬运字节到缓冲区，CPU不参与，配合IDLE中断在对方发完一包数据后通知CPU处理，CPU开销最低，CubeMX里接收DMA设为Circular模式。

### 发送方式

| 方式     | HAL函数                   | CPU开销                     | 适用场景                 |
| -------- | ------------------------- | --------------------------- | ------------------------ |
| 阻塞发送 | `HAL_UART_Transmit()`     | 最高，发送期间CPU被占住     | 调试阶段、简单项目       |
| 中断发送 | `HAL_UART_Transmit_IT()`  | 中等，每字节一次中断        | 有实时性要求、数据量不大 |
| DMA发送  | `HAL_UART_Transmit_DMA()` | 最低，仅启动和完成时CPU介入 | 高波特率、数据量大       |

中断发送和DMA发送有一个共同的坑：传入的**缓冲区在发送完成前不能被修改或释放**。局部数组在函数返回后被回收，中断/DMA还在读那块内存，数据就废了，必须用全局数组或static数组。

工程中最健壮的发送方案是**DMA + 发送环形缓冲区**：应用层随时往缓冲区塞数据，DMA发完一批在 `HAL_UART_TxCpltCallback` 回调中自动取下一批继续发。**串口发送DMA一律用Normal模式**，Circular模式会把同一段数据反复发送。



## DMA

### DMA是什么

DMA（Direct Memory Access，直接内存访问）是一个**独立于CPU的硬件搬运工**。它的唯一工作就是在存储器和外设之间、或者存储器和存储器之间搬运数据，搬运过程中CPU完全不参与，可以去干别的事情。

没有DMA的时候，串口收到一个字节，CPU必须亲自从串口数据寄存器读出来，再写到内存里。如果是连续接收100个字节，CPU就要重复这个动作100次。有了DMA，CPU只需要告诉DMA"从串口数据寄存器搬数据到这个内存地址，搬100个"，然后就可以去执行其他代码了，DMA硬件会自动完成100次搬运。

### STM32F103的DMA结构

F103有两个DMA控制器：**DMA1**（7个通道）和**DMA2**（5个通道，仅大容量型号有）。你的C8T6是中容量，只有DMA1。

每个通道是一条独立的搬运通路，但同一时刻只有一个通道在占用总线。多个通道之间通过**优先级仲裁**决定谁先搬。通道和外设的绑定关系是固定的，不能随便配。比如：

- DMA1_Channel4 → USART1_TX
- DMA1_Channel5 → USART1_RX
- DMA1_Channel6 → USART2_RX
- DMA1_Channel7 → USART2_TX

这个映射关系在参考手册RM0008的DMA章节有完整的表格，CubeMX配置时会自动帮你选对通道。

### DMA传输的三个要素

每次DMA传输需要配置三样东西：

**源地址**——数据从哪里来。如果是串口接收，源地址就是 `USART1->DR`（串口数据寄存器）。

**目标地址**——数据搬到哪里去。通常是你在SRAM里开的一个数组，比如 `uint8_t dmaBuf[256]`。

**传输数量**——搬多少个数据单元。

在此基础上还有几个关键配置项：

**数据宽度**：每次搬运1字节（Byte）、2字节（HalfWord）还是4字节（Word）。串口收发都是按字节的，所以选Byte。

**地址是否递增**：外设端地址一般不递增（因为永远从同一个数据寄存器读），内存端地址递增（每搬一个字节往后挪一位）。

**传输方向**：外设到内存（接收）、内存到外设（发送）、或者内存到内存。

**模式**：Normal模式搬完指定数量就停下来；Circular模式搬完后自动从头开始，形成环形覆盖写入，不需要CPU重新启动。

### DMA的工作流程

以串口DMA接收为例，完整的过程是这样的：

CPU配置好DMA通道的源地址、目标地址、数量、模式等参数，然后启动DMA。之后CPU就可以去干别的了。

串口每收到一个字节，字节进入USART_DR寄存器，串口外设向DMA发出一个请求信号。DMA收到请求后，自动从USART_DR读出这个字节，写入内存缓冲区的当前位置，地址指针加1，剩余计数减1。

这个过程完全是硬件之间的信号交互，CPU不知道也不需要知道。直到某个时机（比如IDLE中断），CPU才来检查DMA搬了多少字节，然后处理数据。

### DMA的三种中断

DMA自身可以产生三种中断：

**传输完成中断（TC）**：所有数据搬完了。在Normal模式下意味着任务结束；在Circular模式下意味着写到了缓冲区末尾，即将回绕到开头。

**半传输完成中断（HT）**：搬了一半。常用于双缓冲技巧——CPU处理前半段的同时DMA继续写后半段。

**传输错误中断（TE）**：搬运出错，比如访问了非法地址。

在串口接收场景下，一般不靠DMA中断来触发处理，而是靠UART的IDLE中断，因为你不知道对方发多少字节，DMA传输完成中断不一定对得上一帧的结束。

### Normal模式 vs Circular模式

**Normal模式**：DMA搬完设定的数量后就停了，不会再搬。下次要接收新数据需要CPU重新启动DMA。适合你明确知道要收多少字节的场景，比如发送一个固定长度的数组。

**Circular模式**：DMA搬完后自动把地址指针归零，从缓冲区开头重新开始写，永远不停。适合串口持续接收的场景，搭配IDLE中断使用。你不用担心"DMA搬完了我还没处理"，因为它一直在循环覆盖写入。但你要确保CPU的处理速度跟得上，否则旧数据会被新数据覆盖。

发送DMA的Circular和Normal模式含义和接收时一样，但**发送场景下几乎不用Circular模式**。

### SRAM与DRAM

| 特性         | SRAM                         | DRAM                                    |
| ------------ | ---------------------------- | --------------------------------------- |
| 存储单元     | 6个晶体管（触发器）          | 1个晶体管 + 1个电容                     |
| 是否需要刷新 | 不需要，通电就一直保持       | 需要，电容几毫秒内电荷流失              |
| 速度         | 快                           | 慢                                      |
| 容量         | 小                           | 大                                      |
| 成本         | 高                           | 低                                      |
| 典型应用     | MCU片内RAM、CPU L1/L2/L3缓存 | 电脑内存条(DDR4/DDR5)、手机内存(LPDDR5) |

F103C8T6 片内 20KB 就是 SRAM，CPU 直接访问，零等待。高端MCU/MPU（如STM32H7、STM32MP1）可通过FMC/FSMC外挂SDRAM扩展。



### 20KB SRAM 的分配

```
20KB SRAM (20480 字节)
├── 全局/静态变量 (.data + .bss)    取决于代码和HAL库用了多少外设
├── 主栈（启动后变为中断栈）         默认 0x400 (1024字节)
├── C库堆                          默认 0x200 (512字节)
├── FreeRTOS堆                     默认 3072 字节
└── 剩余空间                       供链接器分配，不够就编译报错
```

> 主栈在FreeRTOS启动调度器之前被main函数使用，调度器启动之后变成中断处理专用栈。C库堆和FreeRTOS堆是两块独立的内存，互不相干。

编译后查 `.map` 文件可精确查看各段占用。



### 低功耗模式

F103C8T6 支持三种低功耗模式：

| 模式    | 关闭内容          | SRAM保留 | 唤醒源                 | 恢复速度   | HAL函数                      |
| ------- | ----------------- | -------- | ---------------------- | ---------- | ---------------------------- |
| Sleep   | 仅CPU内核         | ✓        | 任何中断/事件          | 最快       | `HAL_PWR_EnterSLEEPMode()`   |
| Stop    | 所有时钟(HSE/HSI) | ✓        | EXTI/RTC闹钟           | 需重配时钟 | `HAL_PWR_EnterSTOPMode()`    |
| Standby | 1.8V域断电        | ✗        | WKUP引脚/RTC/IWDG/NRST | 等同复位   | `HAL_PWR_EnterSTANDBYMode()` |

> Sleep像趴桌上打盹，叫一声就醒。Stop像深度睡眠，闹钟才能叫醒，醒了需要缓一下。Standby像关机了，开机后从头来，之前的状态全没了。

**Stop模式注意**: 唤醒后时钟恢复为HSI(8MHz)，必须重新配PLL回72MHz，否则所有外设波特率、定时器周期都不对。

**Standby模式注意**: SRAM内容丢失、寄存器复位，状态需存到备份寄存器或外部存储。

**通用注意**: 进低功耗前将不需要的外设关闭、IO设为模拟输入或合理状态，避免IO漏电流导致实际功耗远高于理论值。

# 问题记录

### 在USART通信中如何设计一套可靠的帧同步与数据解包机制，使接收端在面对字节丢失、帧边界错位、数据损坏等异常情况时，能够自恢复帧同步并正确提取有效载荷？

> 在使用STM32串口通信时常常会遇到串口接收数据错乱，直接读取无法正确解析数据包的问题

**问题的本质：帧定界问题**

UART是字节流协议，硬件只保证每个字节内部的完整性（起始位、数据位、校验位、停止位），但**不提供字节与字节之间的边界信息**。对接收端来说，它看到的就是一连串字节涌进来，它不知道从哪个字节开始是一帧的起点、到哪个字节结束。这就是帧定界（Frame Delimiting）问题。

如果通信环境理想——没有干扰、没有丢字节——你用最简单的方式（每收满16字节处理一次）也能工作。但现实中会出现几种异常情况。

**字节丢失**：电磁干扰、发送端或接收端缓冲区溢出，都可能导致某个字节没收到。本来期望收16字节凑一帧，丢了一个就变成15字节，后面所有帧的边界永久性地错位了。

**字节插入或错位**：干扰可能导致UART硬件误判一个噪声脉冲为起始位，凭空多出一个字节。或者上电时刻接收端从一帧的中间开始接收，第一帧的后半段和第二帧的前半段被拼成了一个"帧"。

**数据损坏**：传输过程中某个字节的某些bit被翻转，UART的奇偶校验只能检测单bit错误，多bit错误可能漏过。

**解决方案的三个层次**

**第一层：帧同步标记**。在帧的起始位置放置特定的字节序列（帧头），接收端通过识别这个序列来确定一帧的起点。用双字节帧头（如0xAA 0x55）而不是单字节，是因为单字节在随机数据中出现的概率是1/256，而双字节序列出现的概率降到了1/65536，大幅降低了误同步的概率。帧尾的作用类似，提供帧结束的标记，但它不如帧头重要，因为有了帧头和长度字段就已经能确定帧的边界了。

**第二层：差错检测**。在帧中附加校验码（CRC、checksum等），接收端重新计算并与收到的校验码比对。即使帧头碰巧在数据流中被误匹配导致错误同步，校验不通过就能识别出来并丢弃。CRC比简单累加校验（checksum）好在它能检测出更多的错误模式，包括连续bit错误和突发错误。

**第三层：状态机驱动的解析**。接收端不是"攒够N字节再处理"，而是每收到一个字节就根据当前状态判断它是否符合预期。不符合就立刻复位到初始状态重新寻找帧头。这种机制的关键优势是**自恢复能力**：无论当前处于多严重的失步状态，最多丢失当前帧，一旦下一个有效帧头出现就能重新同步。

**接收架构：中断与处理的解耦**

还有一个工程层面的问题：UART中断的触发频率可能很高（115200波特率下每秒约11520次字节中断），如果在中断里做复杂的解析逻辑，可能导致中断执行时间过长，影响系统实时性甚至丢失后续字节。

所以采用**环形缓冲区（Ring Buffer）** 架构：中断里只做一件事——把字节写入缓冲区，立刻返回；主循环或低优先级任务从缓冲区取出字节喂给状态机解析。这样接收和处理在时间上解耦了，即使某一刻处理稍慢，缓冲区能暂存数据不至于丢失。缓冲区大小通常设为帧长的4倍以上，留出足够的余量。



### 为什么DMA接收用Circular而发送不用？

DMA搬完缓冲区最后一个字节后自动回到开头，重新把整个缓冲区再发一遍，永远不停。

想象一下：你发了一帧"你好"，DMA发完后又自动发一遍"你好"，然后又发一遍，无限循环。对方会收到"你好你好你好你好……"。这显然不是你想要的。

**接收端**你不知道对方什么时候发、发多少，所以DMA要一直待命，Circular模式让DMA永远不停地等待接收，有数据就搬，缓冲区满了就回绕覆盖，配合IDLE中断让CPU在合适的时机来取数据。

**发送端**你完全掌控发送时机和内容，每次发的数据都不一样，发完一帧就该停下来等新数据准备好。Normal模式发完即停，完美匹配这个需求。

只有一个极少见的场景会用到：**持续输出固定波形数据**。比如用DMA+DAC输出正弦波，波形数据存在缓冲区里，DMA循环把同样的数据反复送给DAC，产生连续不断的波形。这不是串口通信的场景。



### 为什么HAL和FreeRTOS不能共用SysTick？

**核心冲突在优先级**

SysTick中断里如果跑FreeRTOS的调度逻辑，它的中断优先级必须设为最低（这是FreeRTOS的要求，确保任务切换不会打断其他关键中断）。但HAL库的 `HAL_Delay()` 也依赖SysTick计数，它期望SysTick中断能及时响应。

问题来了：当一个FreeRTOS任务在临界区（调用了 `taskENTER_CRITICAL()`）时，会屏蔽掉优先级等于或低于 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 的中断。SysTick优先级最低，自然被屏蔽。这时候如果临界区里或某个中断服务函数里调了 `HAL_Delay()`，SysTick被屏蔽了，计数器不再增长，`HAL_Delay()` 就**死等永远不返回**，程序卡死。

**分开之后怎么解决的**

CubeMX让你把HAL的时基换到另一个硬件定时器（比如TIM1），并且把这个定时器的中断优先级设得**比FreeRTOS管理的优先级更高**。这样即使FreeRTOS进了临界区屏蔽了低优先级中断，HAL的时基定时器照样能正常触发，`HAL_Delay()` 不会卡死。

简单说就是：SysTick给FreeRTOS专用（优先级最低），另一个定时器给HAL用（优先级更高不受FreeRTOS临界区影响）。
