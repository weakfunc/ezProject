# 第四章 软件设计

软件部分是整个液位测量系统的灵魂所在，硬件搭好了不过是一堆通了电的元件，要让传感器、显示屏、蜂鸣器、蓝牙模块这些散落的部件协同运转起来，全靠软件去调度，去解释数据，去做判断。本章会把笔者在写代码时的一些想法和具体实现一一展开，先讲下位机也就是 STM32 部分的程序，再讲上位机也就是手机 APP 那一侧。

## 4.1 单片机软件设计

### 4.1.1 软件总体框架与任务调度

笔者在动手写代码之前，先思考了一个问题，这个系统在运行时到底要同时干几件事。仔细梳理一下，至少有这么几件，向高精度超声波模块发请求帧并等待回包，定时触发普通超声波采集距地面距离，把测量结果送到 OLED 上去显示，把数据通过串口转发给 ESP32 蓝牙模块，监听 APP 下发的报警阈值，判断液位是否超限并控制蜂鸣器和指示灯。这些事件的时间尺度差异很大，最快的报警响应需要在几十豪秒级别给出，OLED 刷新慢一点没关系两百毫秒一次也够用，蓝牙数据上报一百毫秒一次合适。

如果把所有事情都堆在一个超大的 while 循环里轮训，代码会变得特别难维护，加一个新功能就得在循环里再塞一段，时序也容易乱套。笔者最终决定引入 FreeRTOS 实时操作系统，借助它的任务调度机制，把不同时间尺度的工作分到不同任务里。整个系统主要跑两个任务，一个是周期 10 毫秒的系统级任务，专门负责底层基础库的状态机维护和无线通信链路的数据更新，另一个就是周期 2 毫秒的主应用任务，承担所有业务逻辑。

为什么要把主应用任务设成 2 毫秒这么短的周期。其实笔者不是真的要每 2 毫秒都做完整的业务，而是把 2 毫秒当成一个时间基准格，然后在任务内部用一个计数器 taskCnt 累加，通过对计数器取余来挑出更长的执行周期。比如 taskCnt 每加 1 代表 2 毫秒过去了，那么 taskCnt 对 25 取余等于零的时候，就是 50 毫秒到点了，对 50 取余等于零，就是 100 毫秒到点了，对 100 取余等于零，刚好对应 200 毫秒。这样一个任务里就可以并存好几条不同节奏的时间线，也避免了开太多 FreeRTOS 任务带来的内存开销和切换成本，毕竟 STM32F103C8T6 只有 20KB 的 SRAM，每个任务的栈都得节省着用。

按职责把代码组织成几个明确的部份，最上面是应用层，专门写业务逻辑，下面是驱动层，负责对每个外设做封装，再往下是基础库也就是工具库，提供 CRC、延时、串口字节转发这一类通用的小工具，最底下是 ST 官方的硬件抽像层。调用规则是上面的可以调下面的，但反过来不行，应用层的代码绝对不允许直接去操作 HAL 层的寄存器。这样改一个功能时影响范围被压在了一层之内，调试也清晰。

笔者还约定了一套命名规则，应用任务的入口函数写成 user1TaskInit 和 user1TaskUpdata，注意 Updata 这个拼写，是项目里一直沿用下来的写法，知道有个 e 漏了，但所有任务都这么写就保持一致没去改。任务相关的全局信息打包进一个结构体 user1TaskInfo_t，再声明一个全局变量 user1TaskInfo 让需要的模块共用。驱动层的函数则统一加 DRIVER 前缀，比如 DRIVER_SENSER_Init 是初始化传感器驱动，DRIVER_SENSER_GetDistance 是去读一次距离。所有的内存都是静态分配的，禁用 malloc，单片机里堆栈空间本来就很紧，动态分配出问题以后查起来非常痛苦，索性一开始就堵死这条路。

### 4.1.2 高精度超声波传感器驱动设计

液位测量的精度上限其实是被传感器决定的，所以驱动写得好坏直接关系到整个系统的水平。本系统选用的高精度超声波模块走的是 RS485 总线，跑的是工业上很经典的 Modbus RTU 协议，分辨率 1 毫米，正好对得上任务书要求的 1 毫米变化量分辨率指标。

笔者首先仔细研读了模块的数据手册，搞清楚了它的通信帧格式。读距离用功能码 0x03，目标寄存器地址 0x0000，读一个寄存器，返回值就是当前测距结果，单位是毫米。请求帧固定 8 个字节，从设备地址 0x01 开始，接功能码 0x03，再接寄存器地址高低字节，再接寄存器数量高低字节，最后两个字节是 CRC16 校验。应答帧 7 字节，地址加功能码加字节数加距离高字节加距离低字节再加 CRC 两字节。

有了帧格式，笔者先把请求帧写死成一个数组，因为参数都是固定的，每次都重新构造既浪费 CPU 又容易写错。

```c
static uint8_t ultReqFrame[ULT_REQ_LEN] = {
    0x01U, 0x03U, 0x00U, 0x00U, 0x00U, 0x01U, 0x84U, 0x0AU
};
```

这里的 CRC16 已经预先算好了，硬塞进数组的最后两位。Modbus 用的是查表法或者位操作法计算的 CRC16，多项式 0xA001，初始值 0xFFFF。本驱动里也实现了一份 CRC 计算函数用于校验从模块接收到的应答帧，每个字节先和 crc 异或一下，再循环 8 次，根据最低位决定要不要异或多项式 0xA001，最终拿到 16 位的校验值。计算完拿应答帧带的 CRC 一比，对得上才认这一帧。

接收应答帧这件事笔者用的是中断驱动的字节回调机制。串口每收到一个字节，硬件就触发一次接收中断，中断服务里调用一个回调函数把字节往缓冲区里塞，塞够 7 个字节就把 ready 标志位置 1。

```c
static void __DRIVER_SENSER_UltParseCb(uint8_t port, uint8_t byte){
    (void)port;
    if(ultRspState.cnt < ULT_RSP_LEN){
        ultRspState.buf[ultRspState.cnt] = byte;
        ultRspState.cnt++;
        if(ultRspState.cnt >= ULT_RSP_LEN){
            ultRspState.ready = 1U;
        }
    }
}
```

这种设计的好处是中断里只做最小工作，把字节存下来就走人，主任务负责后续处理。中断时间被压得很短，对其它实时性要求高的任务的影响也就小了。还有个细节是收满 7 字节之后多余的字节会被自动丢弃，避免缓冲区溢出，这一点很重要，因为如果总线上有干扰冒出来一些错位的字节，没有这层保护缓冲区就给写飞了。

真正做一次距离测量的对外接口是 DRIVER_SENSER_GetDistance 这个函数，它是被应用层任务直接调用的核心函数。

```c
uint8_t DRIVER_SENSER_GetDistance(uint16_t *distMm){
    uint16_t crc, rspCrc;
    uint32_t startMs;

    ultRspState.cnt   = 0U;
    ultRspState.ready = 0U;

    SENSER_ULT_DEP_UART_SEND_RAW(ultReqFrame, ULT_REQ_LEN);

    startMs = HAL_GetTick();
    while(ultRspState.ready == 0U){
        if((HAL_GetTick() - startMs) >= SENSER_ULT_TIMEOUT_MS){
            return 0U;
        }
    }

    crc    = __DRIVER_SENSER_Crc16Calc(ultRspState.buf, ULT_RSP_LEN - 2U);
    rspCrc = (uint16_t)ultRspState.buf[ULT_RSP_CRCL_IDX] |
             ((uint16_t)ultRspState.buf[ULT_RSP_CRCH_IDX] << 8U);
    if(crc != rspCrc){
        return 0U;
    }

    if(ultRspState.buf[0]                  != SENSER_ULT_DEVICE_ADDR ||
       ultRspState.buf[ULT_RSP_FC_IDX]     != 0x03U                  ||
       ultRspState.buf[ULT_RSP_BC_IDX]     != 0x02U){
        return 0U;
    }

    senserInfo.distMm = ((uint16_t)ultRspState.buf[ULT_RSP_DH_IDX] << 8U) |
                        (uint16_t)ultRspState.buf[ULT_RSP_DL_IDX];
    senserInfo.isValid = 1U;
    if(distMm != NULL){
        *distMm = senserInfo.distMm;
    }
    return 1U;
}
```

函数的执行思路其实很直白。第一步，把上一次的接收状态清干净，cnt 和 ready 都置零，因为这一次是要发新的请求收新的应答，老数据不能留在缓冲区里。第二步，把那 8 字节的请求帧通过 RS485 总线发出去，发完不需要等待，因为驱动会自己处理 RE 和 DE 信号的方向切换。第三步，进入等待应答的循环，用 HAL_GetTick 函数拿到当前的毫秒时间戳，超过 SENSER_ULT_TIMEOUT_MS 没拿到完整应答就返回 0 表示失败，避免主任务死锁。第四步，应答帧到了之后先校验 CRC，对前 5 个字节算 CRC16，再和应答帧最后 2 字节给的 CRC 比对。第五步，再校验设备地址、功能码和字节数，三者都对得上才认。第六步，从应答帧的第 4、5 字节解析出距离值，高字节左移 8 位再或上低字节，得到 16 位的毫米数，写回 senserInfo 这个公有结构体并通过出参 distMm 返回给调用者。

整个函数返回值的设计是 1 表示成功，0 表示任意一步失败。应用层调用之前会检查返回值，只有成功才用解析出的距离去做后续计算，失败的这一帧直接跳过。这样面对总线偶尔有干扰、模块偶尔丢包这种情况，系统不会被错误数据带偏，丢一帧顶多只是这一周期没有更新值，下一周期再来就是了，对整体测量影响极小。

### 4.1.3 普通超声波传感器驱动设计

普通超声波这边用的是 HC-SR04 模块，工作方式跟前面那个高精度的完全不一样。它没有什么协议，就是非常原始的电平时序方式，你给 TRIG 引脚一个 10 微秒的高电平脉冲，模块就发出一串 40kHz 的超声波，遇到障碍物反射回来后，ECHO 引脚拉高，高电平持续的时间正比于声波往返的时间，知道声速就能算出距离。

这种工作方式在驱动里写起来比 Modbus 要更挑战一点，因为要做精确的微秒级时序。笔者借助了 ARM Cortex-M3 内核里的 DWT 数据观察单元做高精度计时，DWT 里有个循环计数器 CYCCNT，每过一个 CPU 时钟周期就加 1，主频 72MHz 的话一个 cycle 就是 13.9 纳秒，足够测微秒级的脉宽了。

```c
uint8_t DRIVER_SENSER_GetHCSR04Distance(uint16_t *distMm){
    uint32_t startCyc, echoStartCyc, echoEndCyc, elapsedUs;

    SENSER_HCSR04_DEP_TRIG_SET(GPIO_LEVEL_LOW);
    SENSER_HCSR04_DEP_DELAY_US(2U);

    SENSER_HCSR04_DEP_TRIG_SET(GPIO_LEVEL_HIGH);
    SENSER_HCSR04_DEP_DELAY_US(10U);
    SENSER_HCSR04_DEP_TRIG_SET(GPIO_LEVEL_LOW);

    startCyc = SENSER_HCSR04_DEP_GET_CYC();
    while(SENSER_HCSR04_DEP_ECHO_READ() == GPIO_LEVEL_LOW){
        if(SENSER_HCSR04_DEP_ELAPSED_US(startCyc, SENSER_HCSR04_START_TIMEOUT_US)){
            return 0U;
        }
    }

    echoStartCyc = SENSER_HCSR04_DEP_GET_CYC();
    while(SENSER_HCSR04_DEP_ECHO_READ() == GPIO_LEVEL_HIGH){
        if(SENSER_HCSR04_DEP_ELAPSED_US(echoStartCyc, SENSER_HCSR04_ECHO_TIMEOUT_US)){
            return 0U;
        }
    }
    echoEndCyc = SENSER_HCSR04_DEP_GET_CYC();

    elapsedUs = (echoEndCyc - echoStartCyc) / dwtInfo.cycPerUs;

    senserInfo.hcsrDistMm   = (uint16_t)(elapsedUs * 17U / 100U);
    senserInfo.hcsrIsValid  = 1U;

    if(distMm != NULL){
        *distMm = senserInfo.hcsrDistMm;
    }
    return 1U;
}
```

这个函数的实现走得比较踏实。一开始把 TRIG 拉低 2 微秒做个干净的初始电平，然后拉高 10 微秒再拉低，这就是触发脉冲。接下来是两层等待循环，第一层等 ECHO 从低变高，意味着模块开始发超声波了，记录此时的 cycle 计数 echoStartCyc。第二层等 ECHO 从高变低，意味着回波收到了，记录 echoEndCyc。两个 cycle 计数相减，再除以每微秒的 cycle 数，就得到了 ECHO 高电平持续的微秒数。

距离换算这里有个常用公式，声速取 340 米每秒，单程距离等于时间的一半乘声速，毫米单位的距离等于微秒数乘 17 再除以 100。这个公式推导的话是 distMm = elapsedUs × 0.34 / 2 × 1000 / 1000 = elapsedUs × 0.17，写成整数除法就是 elapsedUs × 17 / 100。整数运算比浮点快得多，单片机做这种简单换算非常合适。

两层循环里都加了超时保护，万一 ECHO 引脚没正常变化，比如模块挂了或者前面没有反射面，函数能在 SENSER_HCSR04_START_TIMEOUT_US 或者 SENSER_HCSR04_ECHO_TIMEOUT_US 时间内退出来返回 0，不会卡死任务。这一点对 RTOS 调度下的实时系统来说至关重要，任何一个驱动函数都不能有理论上的无限阻塞。

### 4.1.4 上电标定与液位计算的应用任务

讲完两个驱动，下面看应用任务里把它们怎么编排起来。这就是整个系统最有意思的部分，因为单看任何一个传感器都拿不出最终结果，必须两个传感器配合，再加上数据融合的算法。

整个流程笔者画了一张流程图来梳理思路，参见图 4-1。

![图 4-1 上电标定与液位高度计算流程](.\软件流程图_1.png)

图上看得很清楚，系统上电之后，先连续采集 10 次普通超声波传感器数据，做均值滤波得到模块距离地面的标定值。这个步骤的物理意义是把支架到地面的距离记下来，作为坐标系的零点。然后才进入主循环，每个周期采高精度超声波数据获取距液面距离，做一阶低通滤波平滑掉抖动，再用刚才标定的距地面距离减去当前距液面距离，就是液位高度了。这个算法的核心思想是用两个传感器分别量两段距离，再做差，就避开了支架挂在容器上方时挂得多高这件事的影响。容器换了支架挂得高低不一样也没关系，标定一次就行。

代码层面这套流程在 user1TaskUpdata 这个主任务函数里实现，结合下面这段代码看会更清楚。

```c
if (user1TaskInfo.taskCnt % 25U == 0U) {
    if (user1TaskInfo.calibDone == 0U) {
        user1TaskInfo.calibTimeoutCnt++;

        if (DRIVER_SENSER_GetHCSR04Distance(&rawDist) == 1U) {
            if (rawDist > 0U) {
                user1TaskInfo.calibSum += (float)rawDist;
                user1TaskInfo.calibCnt++;
            }
        }

        if ((user1TaskInfo.calibCnt >= CALIB_SAMPLE_COUNT) ||
            (user1TaskInfo.calibTimeoutCnt >= CALIB_TIMEOUT_COUNT)) {

            if (user1TaskInfo.calibCnt >= CALIB_SAMPLE_COUNT) {
                user1TaskInfo.distToGround_mm = user1TaskInfo.calibSum /
                                                (float)CALIB_SAMPLE_COUNT;
            } else {
                user1TaskInfo.distToGround_mm = CALIB_DEFAULT_GROUND_MM;
            }

            if (DRIVER_SENSER_GetDistance(&rawDist) == 1U) {
                user1TaskInfo.distToLiquid_mm     = (float)rawDist;
                user1TaskInfo.liquidLevelInit_mm  = user1TaskInfo.distToGround_mm -
                                                   user1TaskInfo.distToLiquid_mm;
                user1TaskInfo.liquidLevel_mm      = user1TaskInfo.liquidLevelInit_mm;
                user1TaskInfo.liquidLevelDelta_mm = 0.0f;
            }
            user1TaskInfo.calibDone = 1U;
        }
    } else {
        if (DRIVER_SENSER_GetDistance(&rawDist) == 1U) {
            rawLevel = user1TaskInfo.distToGround_mm - (float)rawDist;

            if ((rawLevel >= LEVEL_VALID_MIN_MM) && (rawLevel <= LEVEL_VALID_MAX_MM)) {
                user1TaskInfo.liquidLevel_mm      = __user1_Filter(rawLevel);
                user1TaskInfo.distToLiquid_mm     = (float)rawDist;
                user1TaskInfo.liquidLevelDelta_mm = user1TaskInfo.liquidLevel_mm -
                                                   user1TaskInfo.liquidLevelInit_mm;
            }
        }
        ......
    }
}
```

这段代码处于 50 毫秒的执行周期里，因为外层判断是 taskCnt 对 25 取余等于零，乘上 2 毫秒的基础周期就是 50 毫秒。在标定阶段也就是 calibDone 还是 0 的时候，每 50 毫秒就调一次 HC-SR04 读距离，累加到 calibSum 上，cnt 加一。一旦 calibCnt 凑够了 10 次，就把和除以 10 得到均值，这就是模块到地面的距离 distToGround_mm。

这里设计了一个超时保护机制 calibTimeoutCnt，每次进来都加 1，加到 40 也就是过了 2 秒还没采集够 10 个有效样本，就直接用默认值 500 毫米兜底。这种健壮性处理在工程项目里非常重要，万一模块刚上电时硬件还没准备好，或者下面没有放容器，或者距离太近触发了盲区，标定怎么也不通过的情况下系统不能就一直卡在标定环节，得有个退路。

标定一旦完成，calibDone 置为 1，就再也不会进上面那个分支了。再调一次高精度超声波拿到当前距液面的距离，做减法得到的就是初始液位高度 liquidLevelInit_mm。后续液位变化量是当前液位减去这个初始值，就是任务书要求的高度变化量功能。

进入正常工作阶段之后，每 50 毫秒读一次高精度超声波，做减法得到原始液位 rawLevel，然后过一个有效性校验，超出 0 到 5000 毫米这个合理范围的数据直接丢弃。校验通过了再进滤波器 \_\_user1_Filter，输出值才作为最终的 liquidLevel_mm。同时计算变化量 liquidLevelDelta_mm，这个值带正负号，正值表示液面比初始高，负值表示低了。

### 4.1.5 滑动均值滤波算法

笔者特意为液位测量设计了一个滑动均值滤波器，因为单次测量难免会有抖动，超声波在介质表面反射时如果有微小波纹或者气泡，就可能给出偏离真值几毫米的读数。任务书里要求静态液位测量误差不大于 ±3 毫米，连续测量读数波动范围不超过 ±3 毫米，这都对滤波提出了硬性要求。

```c
static float __user1_Filter(float newVal)
{
    float   sum;
    uint8_t count;
    uint8_t i;

    user1TaskInfo.filterBuf[user1TaskInfo.filterIdx] = newVal;
    user1TaskInfo.filterIdx = (uint8_t)((user1TaskInfo.filterIdx + 1U) % FILTER_WIN_SIZE);
    if (user1TaskInfo.filterIdx == 0U) {
        user1TaskInfo.filterFull = 1U;
    }

    count = user1TaskInfo.filterFull ? FILTER_WIN_SIZE : user1TaskInfo.filterIdx;
    sum = 0.0f;
    for (i = 0U; i < count; i++) {
        sum += user1TaskInfo.filterBuf[i];
    }
    return sum / (float)count;
}
```

这个滤波器走的是定窗大小循环缓冲区路线，窗口大小定为 5 个样本。每次新数据进来就覆盖最老的一个，整个缓冲区用 filterIdx 这个索引来标记下一个写入位置，写完之后索引加一对窗口大小取余，自然回绕。filterFull 这个标志位是为了处理冷启动阶段没填满缓冲区的情况，刚开始的时候缓冲区只有几个有效样本，要根据 filterIdx 来定真实的有效个数，否则求平均的时候除以 5 会偏小。一旦索引第一次回绕到 0，filterFull 就置 1，从此以后总是除以 5 就行。

为啥选了 5 而不是 10 或者 3 这种数。这个数值是笔者实测时调出来的折中值。窗口越大平滑效果越好，但是响应越迟钝，液面抬升或者下降时数字跟不上变化。窗口太小又起不到滤波作用，单次抖动还是会传到输出。50 毫秒采一次，5 个窗等于 250 毫秒，这意味着液位有一个阶跃变化时，输出大概要 250 毫秒才能跟上。考虑到任务书允许 1 秒的报警延迟，250 毫秒的响应延迟是完全够的。同时 5 个数据求均值，单次抖动会被稀释到原来的五分之一，足够把毫米级的偶然波动压下去。

均值滤波相比一阶低通滤波的好处是参数直观，没有时间常数 alpha 这种需要凭经验调的东西，缺点是吃内存稍微多一点，但 5 个 float 才 20 字节，对 STM32F103 来说微不足道。

### 4.1.6 报警逻辑与阈值响应

报警这块是任务书里很硬的一条要求，液位超出阈值时要在 1 秒内通过蜂鸣器和 LED 给出声光报警。笔者把报警判断逻辑放在了主任务的每个循环里，也就是每 2 毫秒就检查一次，这样响应速度被压在了非常低的水平，远远好于任务书的 1 秒指标。

```c
if ((user1TaskInfo.calibDone     == 1U) &&
    (user1TaskInfo.alarmHigh_mm  > 0.0f) &&
    (user1TaskInfo.liquidLevel_mm >= user1TaskInfo.alarmHigh_mm)) {

    DRIVER_BOARD_RgbOn(BOARD_RGB_R);

    if ((user1TaskInfo.taskCnt % 500U == 0U) && (boardInfo.buzzTimeMs == 0U)) {
        boardInfo.buzzTimeMs = 200U;
    }
} else {
    DRIVER_BOARD_RgbOff(BOARD_RGB_R);
    boardInfo.buzzTimeMs = 0U;
}
```

报警触发的条件是三个 AND 关系，标定已经完成、阈值已经设置成有效值、当前液位高度超过阈值。三者缺一不可。第一个条件防止标定还没结束时由于 liquidLevel 还是 0 导致状态机跳来跳去。第二个条件防止用户没设阈值的时候默认值意外触发。第三个条件就是核心判断，简单直白的大于等于比较。

输出方面，红色 LED 直接调 DRIVER_BOARD_RgbOn 函数点亮，这个函数底层就是把对应 GPIO 拉高。蜂鸣器走的是另一条路，笔者没有让主任务直接控制蜂鸣器的开关，而是写了一个 buzzTimeMs 字段表示要响多少毫秒，由系统级任务每 10 毫秒去读这个字段并递减，递减到 0 就把蜂鸣器关掉。主任务只负责赋值，每 1000 毫秒赋一次 200，意思是每秒响 200 毫秒停 800 毫秒，这样听起来就是滴滴滴的间断声，比一直长鸣更能引起注意。判断条件里加了 buzzTimeMs == 0 的判定，确保只有上一次蜂鸣完成后才下一次赋值，避免快速重复触发把蜂鸣时长不停叠加。

报警解除则相反，只要任意一个条件不满足，就关 LED 关蜂鸣，直接把 buzzTimeMs 也清零让正在响的蜂鸣立刻停下来。这样液位回落时能够立即静音，不会有持续的扰人噪音。

### 4.1.7 OLED 显示刷新逻辑

OLED 显示这部分由 \_\_user1_OledRefresh 函数实现，它是被主任务里 200 毫秒周期那一支调用的。为啥定 200 毫秒一刷而不是更频繁，原因有两个，一个是人眼对几百毫秒级的更新已经感受不出延迟，一个是 I2C 总线上推一屏数据要花十几毫秒，刷得太频繁会浪费 CPU。

```c
static void __user1_OledRefresh(void)
{
    static uint8_t prevCalibDone = 0xFFU;
    char buf[32];

    if (prevCalibDone != user1TaskInfo.calibDone) {
        DRIVER_OLED_Clear();
        prevCalibDone = user1TaskInfo.calibDone;
    }

    if (user1TaskInfo.calibDone == 0U) {
        DRIVER_OLED_ShowString(0,  0, "LiqLevel System ");
        DRIVER_OLED_ShowString(0,  8, "Calibrating...  ");
        DRIVER_OLED_ShowString(0, 16, "Please wait...  ");
        DRIVER_OLED_ShowString(0, 24, "                ");
    } else {
        sprintf(buf, "Lvl:%5d mm   ", (int)user1TaskInfo.liquidLevel_mm);
        DRIVER_OLED_ShowString(0,  0, buf);

        sprintf(buf, "Dlt:%+5d mm  ", (int)user1TaskInfo.liquidLevelDelta_mm);
        DRIVER_OLED_ShowString(0,  8, buf);

        sprintf(buf, "Dst:%5d mm   ", (int)user1TaskInfo.distToLiquid_mm);
        DRIVER_OLED_ShowString(0, 16, buf);

        if (user1TaskInfo.alarmHigh_mm > 0.0f) {
            sprintf(buf, "Alm:%5d mm   ", (int)user1TaskInfo.alarmHigh_mm);
        } else {
            sprintf(buf, "Alm: ----     ");
        }
        DRIVER_OLED_ShowString(0, 24, buf);
    }

    DRIVER_OLED_Refresh();
}
```

函数的开头有个小巧思，prevCalibDone 这个静态变量记录了上次刷新时的标定状态，当本次状态和上次不一样的时候，先把整个屏幕清一遍再写新内容。这是因为标定中和正常工作两种状态显示的字符串完全不同，长度也不一样，如果不清屏直接覆写，旧字符的尾巴会留在屏上变成乱码。但如果每次刷新都清屏，又会有明显的闪烁。所以只在状态切换的瞬间清一次屏，平时直接覆写，这样视觉上既无残留又无闪烁。

显示内容分为两种情况，标定中显示三行英文提示，让用户知道系统正在做啥，正常工作时四行分别显示液位高度、变化量、距液面距离、当前阈值。这里都用了 sprintf 配合定宽格式串，比如 %5d 表示宽度 5 位右对齐，%+5d 表示带正负号的 5 位宽数值，这样数字位数变化时其它字符的位置不会跳动，看着稳定。每个 sprintf 后面那一串空格是为了把字符串补到固定长度，覆盖掉之前可能更长的内容，相当于不清屏的局部擦除技巧。

阈值显示加了一个判断，如果阈值还没设置或者被清零，显示破折号而不是 0，这样语义更清晰，0 容易被理解成阈值是 0 毫米。

### 4.1.8 主应用任务的整体调度

把前面这些零碎的功能模块串起来的就是主任务的入口函数 user1TaskUpdata。函数内部是一个无限的 for(;;) 循环，每次循环开头让 taskCnt 加 1，最后一行调 osDelay(2) 让 FreeRTOS 把任务挂起 2 毫秒，把 CPU 让给其它任务。整个调度表笔者总结成了图 4-2，一目了然。

![图 4-2 液位计算与报警上传流程](.\软件流程图_2.png)

从图上可以看到主任务在标定完成后进入稳态循环，每个循环都做液位高度的计算，然后做阈值判断，超阈值就声光报警，没超就把数据通过蓝牙上传 APP，然后 OLED 显示。这个图实际是把多个时间片合并展示了，真正的代码里这几件事是按不同的取余周期分开执行的，并不是每一个 2 毫秒的循环都全做一遍。

具体调度安排是这样的，每 50 毫秒做一次测距和液位计算，每 100 毫秒把数据写进通信变量池准备发给 APP，每 200 毫秒刷一次 OLED，每 1000 毫秒触发一次 200 毫秒的蜂鸣，每个 2 毫秒循环都做阈值判断和 LED 控制。这样的安排原因如下，测距 50 毫秒是因为一次完整的高精度超声波 Modbus 读取大概要二三十毫秒包含发送和等应答，留点裕量定 50 毫秒比较稳。OLED 200 毫秒不会闪烁。蓝牙 100 毫秒上报频率配合 APP 端的接收节奏。LED 控制必须每个循环都做以保证最快响应。

这里还有一段从 APP 收阈值的代码片段值得说一下。

```c
rxHigh = remoteInfo.remoteVar_RX[0].var_float;
rxLow  = remoteInfo.remoteVar_RX[1].var_float;
if (rxHigh > 0.0f) {
    user1TaskInfo.alarmHigh_mm = rxHigh;
}
if (rxLow > 0.0f) {
    user1TaskInfo.alarmLow_mm = rxLow;
}
```

笔者用的是变量池机制，主控通过串口与 ESP32 蓝牙模块交换数据，蓝牙模块再把数据透传到手机 APP，反方向也走同一条路。变量池本质上是两个 16 槽的数组 remoteVar_RX 和 remoteVar_TX，每个槽是 4 字节的联合体，可以解释成 float、uint32_t 或者 int32_t。应用层只要读写这两个数组，底层就会自动把数据搬过来搬过去，根本不用关心字节序、帧头帧尾、CRC 校验这些底层细节。

读阈值时取了 RX 索引 0 和 1，分别是高低限。判断 rxHigh 大于零才认，避免 APP 还没下发任何阈值时数组里的零值被错误认为是用户设置的阈值零毫米。这种约定看起来有点土，但简单可靠，对于这种数值类配置参数特别合适。

写阈值回 APP 是为了让 APP 的输入框能显示当前实际生效的阈值，做一个回环确认。索引 9 这个槽位写的就是当前 alarmHigh_mm，APP 端在 UI 上显示当前高限那一栏读的就是这里。

```c
remoteInfo.remoteVar_TX[4].var_float  = user1TaskInfo.liquidLevel_mm;
remoteInfo.remoteVar_TX[5].var_float  = user1TaskInfo.liquidLevelDelta_mm;
remoteInfo.remoteVar_TX[6].var_uint32 = (uint32_t)user1TaskInfo.calibDone;
remoteInfo.remoteVar_TX[8].var_float  = user1TaskInfo.distToLiquid_mm;
remoteInfo.remoteVar_TX[9].var_float  = user1TaskInfo.alarmHigh_mm;
```

100 毫秒一次的上报里写了五个 TX 槽位，分别是当前液位、变化量、标定状态、距液面原始距离、当前高报警阈值。注意这里 TX 索引从 4 开始而不是 0，因为前 4 个槽位被无线通信模块自身保留了，到不了手机端。索引 6 写的是标定状态，类型是 uint32 而不是 float，因为它本质上是个布尔标志，用整数更合适。变量池机制的好处在这里就体现出来了，应用层就是普通的赋值操作，看起来跟操作本地变量没啥区别，背后的协议封装、跨芯片传输、字节序转换全被隐藏了。

任务初始化函数 user1TaskInit 比较简单，就是把所有外设驱动调一遍 Init，再把 user1TaskInfo 结构体里的字段都初始化成合理的初值，特别是 alarmHigh_mm 给了 200 毫米的默认值，让系统就算 APP 没连接也能独立工作。

## 4.2 上位机软件设计

### 4.2.1 上位机与下位机通信方案

上位机这边笔者用的是 Android 原生开发，UI 框架选了 Jetpack Compose 配合 Material Design 3，通信走 BLE GATT 协议。整条通信链路完整画出来是这样的，STM32 通过 USART1 跟 ESP32-C3 模块通信，ESP32 作为蓝牙协处理器负责把数据透传到手机。

为啥要用 ESP32 作中转而不是直接给 STM32 配蓝牙模块。一方面 STM32F103 自身没有蓝牙外设，加蓝牙就得加芯片，ESP32-C3 又便宜又稳定，自带的蓝牙协议栈和 Wi-Fi 协议栈成熟度都很高。另一方面 ESP32 跟 STM32 之间用串口通信，协议简单可靠，不会因为蓝牙连接不稳定影响 STM32 的核心功能。即使蓝牙断开手机连不上，OLED 显示和声光报警这些本地功能依然正常工作。

通信帧格式是 STM32 和 ESP32 之间约定好的 16 字节定长帧，APP 跟 ESP32 之间走的是 BLE 的 GATT 服务，每个服务下面有特征值，写特征值就是给单片机发命令，订阅通知就是被动接收单片机上报。APP 端收到 BLE 数据包之后会按照帧格式解析出各个字段，跟下位机的变量池索引对应起来。

APP 端读取数据的代码长这样。

```kotlin
val frame1 = BleProtocol.rxFrames[0x18]
val frame2 = BleProtocol.rxFrames[0x19]
val liquidLevel_mm   = Float.fromBits(frame1?.var4b1 ?: 0)
val liquidDelta_mm   = Float.fromBits(frame1?.var4b2 ?: 0)
val systemStatus     = frame1?.var1b1 ?: 0
val distToLiquid_mm  = Float.fromBits(frame2?.var4b1 ?: 0)
val alarmHighEcho_mm = Float.fromBits(frame2?.var4b2 ?: 0)
```

这里 0x18 和 0x19 是帧 ID，对应下位机不同的 TX 索引段。每帧带两个 4 字节字段加两个 1 字节字段。Float.fromBits 是 Kotlin 里把 32 位整数按 IEEE 754 浮点编码解释成 float 的方法，因为 BLE 帧里数字本质上是字节流，传过来要按双方约定的格式解析。这种解析方式跟下位机那边的 union 联合体形成完美对应。

APP 端发送阈值给下位机的代码也写得很轻巧。

```kotlin
fun sendAlarmThreshold(highMm: Float, lowMm: Float) {
    val frame = BleProtocol.buildTxFrame(
        cmd    = 0x21,
        var4_1 = highMm.toBits(),
        var4_2 = lowMm.toBits(),
        var1_1 = 0,
        var1_2 = 0
    )
    val ok = BleConnectionManager.writeCharacteristic(
        serviceUuid        = UserConfig.esp32_service_1_uuid,
        characteristicUuid = UserConfig.esp32_service_1_characteristic_1_uuid,
        value              = frame
    )
    if (ok) BleConnectionManager.recordOutgoingMessage(
        characteristicUuid = UserConfig.esp32_service_1_characteristic_1_uuid,
        value              = frame
    )
}
```

cmd 取 0x21 是阈值下发命令的约定，两个 var4 字段分别放高低限。toBits 是 Float 转 Int 的方法，跟下位机解析时的 fromBits 对称。组好帧之后通过 writeCharacteristic 写入对应的 GATT 特征值，蓝牙模块收到后会按串口转发给 STM32，主控的变量池里 RX 槽位 0 和 1 就更新了，主任务下一次循环就读到了。整条命令链路从 UI 按钮按下到下位机生效大约 200 到 500 毫秒，肉眼几乎察觉不到延迟。

### 4.2.2 前端用户界面设计

UI 设计这块笔者花了不少心思去琢磨。任务书没有强制要求 APP 长啥样，但既然做了上位机，总不能搞得很丑很难用，否则反倒不如不做。最终的界面效果如图 4-3。

![图 4-3 上位机用户界面](.\软件流程图_3.png)

整个界面是一个可滚动的纵向列表，从上往下依次是项目名称和作者信息标题区，蓝牙连接状态卡片，系统状态卡片，实时测量数据卡片，报警阈值设置卡片。每个功能区都用 Card 控件包裹起来，圆角带浅色背景，看起来层次分明。

笔者为这套界面抽出了两个可复用的 Composable 函数，一个是 HomeSection，专门做带标题的卡片容器，传入标题字符串和内容 lambda 就能渲染一个标准化的卡片。另一个是 ProtoFieldRow，专门用来渲染一行两个字段的标签值对，比如左边显示液位高度，右边显示液位变化量。这两个组件让主页代码看起来非常干净，几乎全是声明式的描述，没有重复的样式代码。

```kotlin
HomeSection(title = "实时测量数据") {
    val isCalib = systemStatus == 0
    Column(
        modifier = Modifier
            .fillMaxWidth()
            .padding(horizontal = 16.dp, vertical = 12.dp),
        verticalArrangement = Arrangement.spacedBy(8.dp)
    ) {
        ProtoFieldRow(
            label1      = "液位高度",
            value1      = if (isCalib) "---" else "%.0f mm".format(liquidLevel_mm),
            label2      = "液位变化量",
            value2      = if (isCalib) "---" else "%+.0f mm".format(liquidDelta_mm),
            value1Color = if (!isCalib && alarmConditionMet) Color.Red else null
        )
        ProtoFieldRow(
            label1 = "距液面距离",
            value1 = if (isCalib) "---" else "%.0f mm".format(distToLiquid_mm),
            label2 = "当前高限",
            value2 = if (isCalib) "---"
                     else if (alarmHighEcho_mm > 0f) "%.0f mm".format(alarmHighEcho_mm)
                     else "未设置"
        )
    }
}
```

值得一提的是 value1Color 这个参数，当系统不在校准中并且报警条件已经满足时，液位高度数字会变成红色，给用户一个非常直观的警示。不然全是黑字一片，超限了也得读完数才知道。这种小细节是好的人机界面跟普通界面的差别所在。

数据显示阶段还要处理一种特殊情况，校准未完成时所有数据都显示破折号而不是真实数字，因为校准没完成液位计算还没开始，显示 0 mm 容易误导用户以为液面是空的。判断条件 isCalib 就是用 systemStatus 是否为 0 来识别的，systemStatus 来自下位机变量池索引，下位机标定完成后会写 1。

阈值设置区用了两个 OutlinedTextField 输入框，一个高限一个低限，键盘类型限定为数字键盘 KeyboardType.Number，这样用户点击输入时手机弹出来的就是数字小键盘而不是全键盘，输入更快。下面一个全宽 Button 触发提交。

```kotlin
Button(
    onClick = {
        val high = highInput.toFloatOrNull()
        val low  = lowInput.toFloatOrNull()
        when {
            high == null || low == null  -> Toast.makeText(context,
                "请输入有效数值", Toast.LENGTH_SHORT).show()
            high <= 0f || low <= 0f      -> Toast.makeText(context,
                "阈值须大于0", Toast.LENGTH_SHORT).show()
            high > 5000f || low > 5000f  -> Toast.makeText(context,
                "阈值超出范围（最大5000mm）", Toast.LENGTH_SHORT).show()
            high <= low                  -> Toast.makeText(context,
                "高限须大于低限", Toast.LENGTH_SHORT).show()
            else                         -> sendAlarmThreshold(high, low)
        }
    },
    modifier = Modifier.fillMaxWidth()
) {
    Text("设置阈值")
}
```

按钮的点击处理是一连串的合法性检查，输入是不是有效数字、是不是大于零、是不是不超过 5 米的物理上限、高限是不是大于低限，任何一项不通过都用 Toast 弹一个简短提示告诉用户哪里错了，全部通过才真正调 sendAlarmThreshold 把数据发出去。这种前置校验是 UI 设计的基本功，把不合理输入挡在客户端，免得发到下位机再判断，节省蓝牙带宽也节省用户时间。

笔者对界面控件的选择有个原则，下位机给手机的数据用文本显示，手机给下位机的控制用按钮和输入框，不用 Slider 或 SeekBar 这种滑动控件。原因是滑动控件对手指精度要求高，毫米级阈值用滑动设置很别扭，输入框配数字键盘反而又快又准。这是笔者在上位机界面交互上的一个工程化判断。

### 4.2.3 后端逻辑与状态管理

Compose 的状态管理跟传统的 Android View 体系很不一样，所有 UI 跟状态绑定，状态变了 UI 自动刷新。笔者用了几个关键的状态变量来管理报警弹窗的显示逻辑。

```kotlin
var showAlarmDialog by remember { mutableStateOf(false) }
var alarmSnoozed    by remember { mutableStateOf(false) }
var alarmCooldown   by remember { mutableStateOf(false) }

val alarmConditionMet = alarmHighEcho_mm > 0f && systemStatus != 0
                        && liquidLevel_mm > alarmHighEcho_mm

LaunchedEffect(alarmHighEcho_mm) { alarmSnoozed = false }

LaunchedEffect(alarmConditionMet, alarmCooldown, alarmSnoozed) {
    if (alarmConditionMet && !alarmSnoozed && !alarmCooldown && !showAlarmDialog) {
        showAlarmDialog = true
    }
}
```

showAlarmDialog 控制弹窗是不是可见。alarmSnoozed 是用户主动选择不再提醒的标志。alarmCooldown 是确认了之后的冷却期标志。三个状态围绕弹窗的显示生命周期协同工作。

alarmConditionMet 是一个派生状态，从下位机数据计算出来，三个条件全满足才视为报警条件成立。LaunchedEffect 是 Compose 提供的副作用机制，给定的依赖发生变化时会重新执行 lambda 体。这里第一个 LaunchedEffect 监听 alarmHighEcho_mm 变化，意思是用户改了阈值后把已静音状态重置，因为用户既然主动改了阈值表示他想重新关注报警了。第二个 LaunchedEffect 监听报警条件、冷却、静音三个状态的组合，只要条件满足又没被关掉，就把弹窗打开。

弹窗本身是一个 AlertDialog，提供两个按钮，确认和不再提醒。

```kotlin
AlertDialog(
    onDismissRequest = {},
    title            = { Text("液位超限报警") },
    text             = {
        Text("当前液位 %.0f mm 已超过设定高限 %.0f mm！"
             .format(liquidLevel_mm, alarmHighEcho_mm))
    },
    confirmButton = {
        TextButton(onClick = {
            showAlarmDialog = false
            alarmCooldown   = true
            coroutineScope.launch {
                delay(10_000L)
                alarmCooldown = false
            }
        }) { Text("确认") }
    },
    dismissButton = {
        TextButton(onClick = {
            showAlarmDialog = false
            alarmSnoozed    = true
        }) { Text("不再提醒") }
    }
)
```

确认按钮把弹窗关掉，进入 10 秒冷却期，10 秒内即使条件依然满足也不再弹。这是为了避免用户刚关弹窗马上又弹出来的烦扰。冷却时间用协程 delay 实现，coroutineScope 是从 rememberCoroutineScope 拿到的，依附于当前 Composable 的生命周期。

不再提醒按钮则把弹窗关掉并永久静音，直到用户改阈值才会重置。这两种处理对应两种典型用户场景，确认是我看到了但事情还没处理完待会再说，不再提醒是我知道了不要再来烦我。给用户选择权而不是强制弹窗，是对用户尊重的体现。

onDismissRequest 是空 lambda 这点也有意为之，意思是弹窗不能通过点对话框外面或者按返回键关闭，只能通过两个按钮关。这种设计针对的是高优先级警告，避免用户不小心点掉而错过重要信息。

整个后端逻辑就这么些状态变量和几个副作用，加起来不到 30 行代码就把一个相当复杂的报警交互流程实现了。这就是声明式 UI 的魅力所在，告诉框架什么状态对应什么界面，框架自己负责保持一致，开发者不用手动同步。

# 第五章 机械外观设计

机械结构虽然不是这个课题的考核重点，但一个真正能用的产品离不开稳固的物理载体。笔者用 SOLIDWORKS 2025 做了机械结构的设计，主要解决两个核心需求，第一个是把高精度超声波模块、普通超声波模块和电路板这三样东西按系统总体方案要求的姿态固定起来，第二个是让整个装置可以方便地架设在容器边缘。下面分零件展开说明。

## 5.1 一体化传感器电路板支架

支架是整个系统的骨架零件，相当于把所有电气部件捏合成一个完整装置的桥梁。零件设计图见图 5-1。

![图 5-1 一体化传感器电路板支架三维图](.\机械_1.png)

图中可以看到支架整体是一个长条形扁平结构，前后两端各有一个开口槽位，中间是一个略低的承载平台。前端的细长开槽是用来安装高精度超声波模块的，开槽的形状跟模块底部的两个螺丝孔相对应，模块卡进去之后用螺丝从下方固定，超声波探头自然朝向地面方向，正好对着待测的液面。后端的方形开口是普通超声波模块也就是 HC-SR04 的安装位，HC-SR04 的两个圆形换能器从这个开口探出去，朝向支架的下方。中间的承载平台尺寸跟笔者绘制的 PCB 板大小一致，PCB 用螺丝从下方上来固定到平台上，电池外接。

这样的布局是有讲究的。两个超声波模块为啥要前后分开装，前面装高精度模块测液面，后面装普通模块测地面。理由是这两个模块的工作方向虽然都是向下，但是探测目标不一样，高精度模块对的是液面，需要正对待测容器的开口位置，普通模块对的是地面或者容器外缘的某个固定参考面，作为标定时的零点。两者分开有一定距离避免互相干扰，超声波模块挨太近的话发射时序如果没错开，回波会被对方的探头收到，造成测量错误。机械上分开是最简单可靠的解决方案，两个模块前后分布相隔大约 12 厘米，这个距离一方面物理隔离了串扰，另一方面也让支架两端各有一个稳定的支撑点，把支架架在容器边缘的时候不会绕一根轴乱转。

支架两端那两条细长的腰形孔不是装饰，它们是用来挂住容器边缘的搭爪结构。容器口宽度可能从十几厘米到二十几厘米不等，如果做成固定的卡口，换个容器就没法用了，做成开槽形态就有了一定的位置调节范围，配合螺栓和螺母可以夹紧不同厚度的容器壁。这种设计思路在工程上叫做参数化适配，让一个零件能服役于一组相似但又不完全相同的应用场景。

材料方面笔者选择了铝合金加工，铝合金的好处是质量轻、强度够、加工性好、抗腐蚀。液体测量场合下支架免不了会沾到水汽或者飞溅的液滴，铝合金不容易生锈。如果选 ABS 塑料 3D 打印则成本更低，但塑料件长期受重和水汽影响容易变形老化，对于一个要长时间稳定工作的测量装置不够理想。质量方面整个支架大约 80 克，加上两个超声波模块和电路板总体不到半斤，单手就能拿稳。

支架的厚度选了 3 毫米，这个数据是查铝板规格选了一个折中值。再薄会感觉飘容易颤动，再厚就太重了，3 毫米是机械强度跟便携性之间的平衡点。承载平台跟两端搭爪之间通过弯折一体成型，弯折角的位置和角度经过 SOLIDWORKS 的简单受力仿真校验过，常规使用下不会变形。

## 5.2 系统装配实物展示

图纸归图纸，做出来才算数。笔者按照设计图加工出支架并组装上各部件之后的真实样子见图 5-2。

![图 5-2 系统装配后实物](.\机械_2.png)

照片里可以看到完整的系统已经架在了一个透明塑料水箱的边缘上。支架的搭爪部分牢牢钩住了水箱顶部的内沿，整个装置稳稳地伸向水箱中心区域，前端的高精度超声波模块朝下对着水箱内部的液面，黑色塑料外壳里面就是那对超声波换能器。后端的 HC-SR04 模块圆形探头则朝向水箱底部或者外侧的地面参考位置。中间的电路板上能看到 STM32 最小系统板、RS485 转 TTL 模块、ESP32-C3 蓝牙模块整齐地排布在 PCB 上，几个红色 LED 在工作中亮起，显示主控芯片正常运行。OLED 显示屏装在支架的左侧，屏幕上正显示着实时测量结果，液位数值清晰可读。锂电池作为独立模块用扎带绑在支架后侧，输出线接到电路板的供电接口。

照片右下角是手机端 APP 的截屏内容，画面里 BLE 已成功连接到 ESP32C3_PHONE 这个设备，信号强度 -54 dBm 表示连接质量良好。系统状态显示正常工作，实时测量数据栏给出液位高度 351 毫米，液位变化量正 7 毫米，距液面距离 149 毫米。这一切跟支架上 OLED 显示的数字基本对得上，毫米差异属于两端刷新时间不同步带来的瞬时偏差，在容许的范围内。报警阈值设置栏正下方有个紫色的设置阈值按钮和两个输入框。手机连接的物理位置就在水箱边上，方便对照实物验证数字的准确性。

把图 5-1 的设计图跟图 5-2 的实物对比看，会发现实物完全实现了设计意图，两个传感器位置对、姿态对、间距对，电路板装得稳，整体外观也比较干净整齐。从这一刻开始整个系统才是真正可用的，不再是一堆电路图和代码注释里描述的概念。一个完整的项目最后能拍出这样一张照片，是对前面所有设计工作最实在的回报。

机械部分到这里设计与制作就告一段落。整体来看零件数量被笔者刻意压在了最少，只用一个一体化支架就解决了两个传感器和一块 PCB 的安装、容器边缘的挂载、机械稳固性几个问题。这种少零件多功能的设计思路，对学生作品来说既能控制成本和加工难度，又能体现工程设计的整体观。
